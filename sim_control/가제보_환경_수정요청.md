# 가제보 환경 수정 요청

`new_robot` 패키지(`jy-update` 브랜치) 기준으로 확인한 사항입니다. 제어 노드는
`tests/sim_control/`에 작성해 두었고, 아래 항목이 반영되어야 검증이 가능합니다.

우선순위 순으로 A → E 입니다. **A와 B가 핵심**이고, C·D·E는 그 다음입니다.

## A. IMU 축 정합 (차단 요소)

### 증상

`gazebo.launch.py`의 스폰이 `-R -1.5708 -P 1.5708`로 로봇을 회전시켜 세우는데,
base IMU가 붙은 `root`는 속이 빈 링크(`<link name="root" />`)라서 그 회전이
센서 프레임에 그대로 남습니다. 회전행렬을 계산하면:

| 센서 축 | 실제 방향 (base IMU) | 실제 방향 (tray IMU) |
|---|---|---|
| +X | **−Z (아래)** | **−Z (아래)** |
| +Y | −X (후방) | +X (전방) |
| +Z | +Y (좌측) | −Y (우측) |

즉 **정지 상태에서 중력이 Z가 아니라 X에 실립니다** (`linear_acceleration.x ≈ −9.81`).
제어 코드는 REP-103(Z 상방)을 가정하므로, 이 상태에서는 목표각이 −45°로 고정되어
트레이가 조인트 한계에 처박힙니다. 두 IMU의 순열이 서로 다른 것도 문제입니다.

### 확인 방법

로봇을 평지에 정지시킨 상태에서:

```bash
ros2 topic echo /imu --once
ros2 topic echo /imu_tray --once
```

- `linear_acceleration.z ≈ ±9.81`, `x ≈ 0` → 정상
- `linear_acceleration.x ≈ −9.81`, `z ≈ 0` → 수정 필요 (현재 이 상태로 예상)

제어 노드도 시작 시 자동 진단을 출력합니다.

### 수정

`<sensor>`에 `<pose>`를 넣어 센서를 정렬합니다. 링크가 돌아간 만큼 센서 쪽에서
역으로 돌려 상쇄하는 방식입니다. 계산해 둔 값입니다.

```xml
<gazebo reference="root">
    <sensor name="chassis_imu" type="imu">
        <pose>0 0 0 1.5708 0 -1.5708</pose>
        <always_on>true</always_on>
        <update_rate>100</update_rate>
        <topic>imu</topic>
    </sensor>
</gazebo>
<gazebo reference="default_4">
    <sensor name="tray_imu" type="imu">
        <pose>0 0 0 -1.5454 0 1.5091</pose>
        <always_on>true</always_on>
        <update_rate>100</update_rate>
        <topic>imu_tray</topic>
    </sensor>
</gazebo>
```

tray IMU는 **탱크 기하 프레임과 정렬**되는 것이 중요합니다(`water_tank_joint`의
`rpy="0.000498 1.545365 3.080375"` 고려). 위 값은 그 기준으로 계산했습니다.

> 더 근본적으로는 스폰 RPY를 `0 0 0`으로 두고 그 회전을
> `hanging_node_to_root_joint`에 흡수시켜 `root`를 Z-up·X-전방인 정상 `base_link`로
> 만드는 방법이 있습니다. 그러면 odom·TF·RViz까지 전부 정리됩니다. 다만 전방
> 방향을 정하려면 `/cmd_vel`을 줘 보고 odom이 어느 축으로 증가하는지 확인해야
> 하므로, 급하면 위 `<pose>` 방식이 빠릅니다.

**임시 우회**: 수정 전이라도 제어 노드에 프리셋을 주면 돌아갑니다.

```bash
python3 gimbal_leveling_controller.py --ros-args -p use_sim_time:=true \
    -p base_axis_preset:=cad_rotated_base -p tray_axis_preset:=cad_rotated_tray
```

## B. Housner 등가 진자 추가 (액체 표현)

### 왜 필요한가

가제보(gz sim)에는 **유체 물리가 없습니다.** 현재 `water_tank`는 질량 0.5kg
강체 껍데기이므로:

- 출렁이는 물이 짐벌에 **반력을 전혀 주지 않습니다** → 제어 문제가 인위적으로 쉬움
- 슬로싱을 **계측할 수단이 없습니다** → 보고서에 넣을 지표가 안 나옴

슬로싱 액체를 "고정 질량 m₀ + 등가 진자 m₁"으로 치환하는 것이 표준
등가 기계 모델(Housner/Abramson, NASA SP-106 계열)입니다. 진자를 탱크 안에 넣으면
(1) 출렁임이 짐벌에 실제 반력을 주고 (2) **진자각이 슬로싱 지표**가 됩니다.

### 파라미터 (R=55mm, h=90mm 기준)

`water_tank.stl` 내반경 55mm(외 60mm − 벽 5mm), 정지수위 90mm로 계산했습니다.

| 항목 | 값 |
|---|---|
| 전체 물 질량 | 0.8553 kg |
| 1차 슬로싱 모드 | ω₁ = 18.078 rad/s (2.877 Hz, T = 0.3476 s) |
| 슬로싱 질량 m₁ | 0.1654 kg |
| 고정 질량 m₀ | 0.6899 kg |
| 등가 진자 길이 L | 30.02 mm |
| 슬로싱 질량 높이 h₁ | 62.93 mm (탱크 바닥 기준) |
| 피벗 높이 | 92.94 mm (탱크 바닥 기준) |
| 회전 감쇠 (ζ=0.01) | 5.39e-5 N·m·s/rad |

메시가 z = −90mm ~ +90mm로 생성되므로(`generate_water_tank_mesh.py`), 탱크 바닥은
`water_tank` 링크 좌표 z = −0.09 입니다. 따라서 **피벗은 z = −0.09 + 0.09294 = +0.00294**.

### URDF 추가 (복사해 쓰시면 됩니다)

URDF에는 spherical 조인트가 없으므로 직교 revolute 2개로 유니버설을 만듭니다.

```xml
<!-- ===== Housner 등가 슬로싱 진자 ===== -->
<!-- 중간 링크: 피벗에 있어 진자 모멘트에 기여하지 않음(질량은 m0에 흡수) -->
<link name="slosh_gimbal_x">
    <inertial>
        <mass value="0.005" />
        <origin xyz="0 0 0" rpy="0 0 0" />
        <inertia ixx="1e-6" ixy="0" ixz="0" iyy="1e-6" iyz="0" izz="1e-6" />
    </inertial>
</link>

<link name="slosh_bob">
    <inertial>
        <mass value="0.1654" />
        <origin xyz="0 0 0" rpy="0 0 0" />
        <inertia ixx="2.65e-5" ixy="0" ixz="0" iyy="2.65e-5" iyz="0" izz="2.65e-5" />
    </inertial>
    <!-- 시각화용. 화면에서 출렁임이 보이도록 (물리에는 영향 없음) -->
    <visual>
        <origin xyz="0 0 0" rpy="0 0 0" />
        <geometry><sphere radius="0.012" /></geometry>
        <material name="slosh_blue"><color rgba="0.2 0.6 1.0 0.8" /></material>
    </visual>
</link>

<joint name="slosh_pendulum_x" type="revolute">
    <origin xyz="0 0 0.00294" rpy="0 0 0" />
    <axis xyz="1 0 0" />
    <parent link="water_tank" />
    <child link="slosh_gimbal_x" />
    <limit lower="-0.6" upper="0.6" effort="1.0" velocity="20.0" />
    <dynamics damping="5.39e-5" friction="0.0" />
</joint>

<joint name="slosh_pendulum_y" type="revolute">
    <origin xyz="0 0 -0.03002" rpy="0 0 0" />
    <axis xyz="0 1 0" />
    <parent link="slosh_gimbal_x" />
    <child link="slosh_bob" />
    <limit lower="-0.6" upper="0.6" effort="1.0" velocity="20.0" />
    <dynamics damping="5.39e-5" friction="0.0" />
</joint>
```

두 번째 조인트의 `origin z = -0.03002`가 진자 길이 L입니다.

### 함께 조정할 것

`water_tank` 링크 질량을 **탱크 껍데기 질량 + m₀(0.6899 kg)** 로 맞춰 주세요.
현재 0.5 kg인데 **물만 0.855 kg**이라 과소합니다. 진자 m₁은 위에서 별도
링크로 빠졌으니 중복 계산되지 않습니다.

`fix_new_robot_urdf.py`로 URDF를 재생성하시면 이 블록이 지워질 수 있으니,
스크립트에 추가하거나 재생성 후 다시 붙이는 방식이 필요합니다.

### 검증

`slosh_pendulum_x` 각도가 정지 상태에서 0 근처, 가감속 시 흔들리다 감쇠하면
정상입니다. 주기가 약 0.35초여야 합니다(f₁ = 2.877 Hz).

> 참고: 이 모델은 1차 모드 선형 소진폭 이론입니다. 큰 진폭이나 파도 깨짐은
> 표현하지 못합니다. 보고서에 쓸 때 "등가 기계 모델"임을 명시하는 것이 정확합니다.

## C. 물리 파라미터 정리

### 위치 컨트롤러 게인

현재 `p_gain=20, i_gain=0, d_gain=15`입니다. `d/p = 0.75초`인데 통상적인 위치
루프는 0.01~0.1초입니다. **7~75배 과합니다.** 이러면 조인트가 굼떠져서 100Hz로
바뀌는 목표각을 따라오지 못하고, ZV 입력성형이나 게인 스케줄링 효과가 내부 루프에서
다 뭉개집니다.

```xml
<d_gain>1.5</d_gain>   <!-- 15 -> 1.5 (d/p = 0.075) -->
```

이전에 알려주신 값이 `p=25, i=0, d=1.5`였는데 브랜치에는 `d=15`로 되어 있습니다.
진동을 잡으려고 올리신 것으로 보이는데, 그 진동의 원인은 **A의 축 문제**(목표각이
−45°로 고정되어 조인트 한계에 눌린 채 떠는 것)일 가능성이 높습니다. A를 먼저
고친 뒤 판단하시는 편이 좋겠습니다.

### 조인트 dynamics

같은 이유로 올라간 것으로 보입니다.

```xml
<dynamics damping="0.05" friction="0.01" />   <!-- 0.2 / 0.05 -> 되돌림 -->
```

### effort

`effort="10"` (N·m)는 짐벌 모터로는 과다합니다. GL60 계열 직결 구동은 정격
0.3~1 N·m 수준일 것으로 보이는데, `Gimbal Motor Drive User Manual.pdf`가
이미지 기반이라 텍스트 추출이 안 됩니다. **매뉴얼에서 정격 토크를 확인해
반영 부탁드립니다.**

논문 서론이 "모터의 기계적 한계로 인해 제어의 끊김 현상이 발생"하는 문제를
다루고 있어서, 토크 한계가 비현실적으로 크면 검증하려는 문제 자체가 사라집니다.

### 관성모멘트 / 질량

- **70개 링크 중 40개**가 관성모멘트 1e-7 kg·m² 미만입니다. gz 솔버 지터·발산의
  대표적 원인입니다
- 총 질량 1.025 kg (그중 water_tank 0.5 kg). CAD 기본 밀도 값으로 보입니다
- mesh collision이 61개입니다 (`fix_new_robot_urdf.py`가 모든 visual에 STL
  collision을 자동 생성). 접촉이 필요한 바퀴·바닥 외에는 primitive로 바꾸면
  훨씬 안정적이고 빨라집니다

## D. 확인 요청

**조인트 한계 ±0.4363 rad (±25°)** 가 GL60II의 실제 기구 한계인가요, 아니면
`fix_new_robot_urdf.py`에서 임의로 정한 값인가요?

원본 서보 코드의 PWM 범위를 역산하면 약 ±50° 상당의 보정 여유가 있었어서,
±25°는 그 절반입니다. 제어 노드의 `joint_limit_rad`를 맞춰야 합니다.

## E. `/joint_states` 발행 추가

현재 조인트 상태를 발행하는 플러그인이 없습니다. 다음 두 곳에 필요합니다.

- **모터 피드백** — 상태기계의 `MOTOR_CHECK`. 실물에서는 GL60II 피드백이지만
  시뮬레이션에서는 조인트 상태가 그 역할을 합니다
- **Housner 진자각 로깅** — B의 슬로싱 지표

### URDF

```xml
<plugin filename="gz-sim-joint-state-publisher-system"
        name="gz::sim::systems::JointStatePublisher">
</plugin>
```

### launch 브릿지

```python
joint_state_bridge = Node(
    package='ros_gz_bridge',
    executable='parameter_bridge',
    arguments=['/world/empty/model/new_robot/joint_state'
               '@sensor_msgs/msg/JointState[gz.msgs.Model'],
    remappings=[('/world/empty/model/new_robot/joint_state', '/joint_states')],
    output='screen',
)
```

`LaunchDescription` 목록에도 추가해 주세요. 월드 이름은 현재 `empty.sdf`를 쓰고
있으니 `empty`입니다.

> 없어도 제어 노드는 `require_motor_feedback:=false`(기본값)로 돌아갑니다.
> 다만 슬로싱 지표를 못 남기므로 보고서 자료가 안 나옵니다.

## 검증 절차

A~E 반영 후 순서대로 확인하면 됩니다.

```bash
# 1. 축 정합 확인
ros2 topic echo /imu --once          # 정지 시 z에 ±9.81

# 2. 빌드 & 실행
colcon build --packages-select new_robot
source install/setup.bash
ros2 launch new_robot gazebo.launch.py

# 3. 제어 노드 (별 터미널)
python3 gimbal_leveling_controller.py --ros-args -p use_sim_time:=true \
    -p log_csv_path:=/tmp/run_zv.csv

# 4. 상태 확인 — READY -> ACTIVE 로 가는지
ros2 topic echo /gimbal_state

# 5. 명령 발행 확인
ros2 topic echo /gimbal_roll_cmd

# 6. GUI로 차체를 기울여 트레이가 반대로 움직이는지 (부호 검증)

# 7. 주행 외란
ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/Twist \
    '{linear: {x: 0.5}}'

# 8. ZV ON/OFF 비교
#    -p enable_zv:=false 로 한 번 더 기록한 뒤
python3 analyze_log.py /tmp/run_nozv.csv /tmp/run_zv.csv --plot compare.png
```

제어 노드는 `tests/sim_control/`의 `gimbal_leveling_controller.py` +
`gimbal_control_core.py` 두 파일이며 같은 폴더에 두면 됩니다. 상세는 같은 폴더의
`README.md`를 참고해 주세요.

## 참고: 검증된 것 / 안 된 것

제어 코어는 플랫폼 독립이라 ROS 없이 단위 시험을 돌렸습니다. **77개 검사 통과**
(`python3 test_core.py`) — 역기구학 왕복, 경사 정지 시 트레이 절대 수평(base 10°
→ 조인트 −10.000000°), ZV 임펄스 응답·DC 이득, 상태기계·FAULT 전이 등입니다.

**가제보에서의 실행은 검증하지 못했습니다.** 로컬에 ROS2/gz가 없어서입니다.
실행 중 에러나 이상 동작이 있으면 로그와 함께 알려주시면 바로 잡겠습니다.
